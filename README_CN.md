# SentinelX Kuroko

**连接日志分类引擎 — 架构说明（交接文档）**

> English version: [README.md](README.md)

本仓库有两个独立但结构对称的 Python 脚本，用来对 IDC 机队的连接日志做安全分类。
本文件供后续维护者/AI 快速理解设计，无需通读代码。

## 0. 本仓库在 SentinelX 中的位置

**SentinelX 整体并非开源项目。** 为避免混淆，项目已拆分为两个独立仓库，
**仅 SentinelX Kuroko（即本仓库）开源**：

| 组件 | 职责 | 状态 |
|---|---|---|
| **SentinelX Misaka** | 数据采集与网络管控：原始数据获取、流量拦截、网站封锁、连接日志记录及其它相关安全功能 | **闭源** |
| **SentinelX Kuroko**（本仓库） | 对采集到的网络日志做分析的开源日志分析算法 | **开源**（CC BY-NC 4.0） |

Kuroko 消费 Misaka 产出的连接日志，但不依赖 Misaka 的代码：它只从磁盘读取纯文本快照（见 §3），
可以完全独立运行。

### 版本号

因本次拆分，此前的统一版本号不再适用。**Misaka 与 Kuroko 此后各自维护独立的版本历史，
均从 `v1.0.0` 重新开始。** 两者版本号互相独立，**不会**保持同步 —— 各自遵循各自的开发与发布周期。

**本仓库当前版本：Kuroko v1.2.0**（变更记录见 §12）。

## 1. 它解决什么问题

机队每台节点每天导出两份「连接日志」快照（最近 24 小时）：
- **成功连接**（info）：TCP 真的建成了。
- **失败连接**（warning）：连接尝试失败。

原始日志已按 `origin(内网源IP) → 目的地(host:port) → 次数` 聚合。引擎的任务：从中挑出
**规模化扫描 / 端口探测 / 僵尸网络行为 / P2P**，同时**尽量不误杀正常业务**（重点：客户自建
的 REALITY 代理节点会大量访问 visa.cn/qualcomm.cn 等大厂域名做 SNI 伪装，绝不能当威胁）。

## 2. 两个脚本

| 脚本 | 处理 | 特有点 |
|---|---|---|
| `classify_logs.py` | 失败连接（warning_*） | 高危端口集**不含** 22 |
| `classify_info_logs.py` | 成功连接（info_*） | 高危端口集**含** 22（成功=已得手更严重），且有 `xref` 轴与同日期 warning 结果交叉比对；成功语境阈值更紧 |

两者共用同一套解析、跨天关联、机队抑制、报告渲染逻辑（各自复制，保持文件独立）。
`classify_info_logs.py` 会 `import classify_logs` 来复用 warning 引擎做交叉比对。

## 3. 输入

每台节点每种日志每天产出一份 24 小时快照（这部分属于 SentinelX Misaka），已按
`origin(内网源IP) → 目的地(host:port) → 次数` 聚合。引擎自动发现所有可用日期并全部载入，**无需参数**。
任何能输出同样聚合文本格式的日志来源都可以，跑 Kuroko 并不需要 Misaka。

原始导出有一点对算法有影响：它会把占某 origin 流量 ≥75% 的单一目的地当「高频噪音」剔除。
`effective_dests()` 在检测前**把这条目的地重新放回来**（否则一片 telnet 洪水若被当噪音剔除
就会整条漏判），但不改变 total 计数语义。

### 时间戳字段（2026-07-29 起新增，可选）

命中数 ≥2 的目的地行末尾可能带一段时间戳尾缀
`[t 首次~末次 avg=平均间隔 secs=命中的不同秒数]`，例如：

```
  www.visa.cn:443: 1485  [t 00:00:30~23:59:48 avg=58.2秒 secs=1484]
```

`DEST_RE` 用一个**可选**的非捕获尾缀组匹配它，有/无此字段的行都能解析；解析出的 4 个值统一
换算成秒存在 `Dest.first_s / last_s / avg_sec / distinct_secs`（旧格式与单次命中行留 `None`）。
`first_s/last_s` 是「单域名连接风暴」轴（§5.6）的输入——该轴用 `count ÷ (末次 − 首次)` 算持续速率。
`avg_sec` 与 `distinct_secs` 目前**不参与任何判定**：`avg_sec` 只用于丰富 `openai_auth` 轴的 reason
文案（已用数据验证过，正常用户的鉴权请求也经常是几秒内的小突发，拿「突发」本身当信号会误杀）；
`distinct_secs` 曾是 v1.1.0「域名并发异常」轴的唯一输入，该轴已在 v1.2.0 被推翻重写（见 §5.6），
字段保留但不再被读取。

> 改这段正则要小心：旧格式行完全靠尾缀可选（`(?:...)?`）才不被破坏。若哪天上游格式再变、
> 尾缀彻底不匹配，`parse_file` 会**静默丢弃整行**而不是报错——务必拿一天新数据实际跑一遍
> `parse_file`，抽查 `by_port` / `domain_counts` 对不对得上，而不是只看脚本有没有报错。

## 4. 严重度模型

```
CLEAN  <  INFO  <  WATCH  <  SUSPICIOUS  <  MALICIOUS
```
- **INFO**（2026-07-31 新增，比 WATCH 更低）：探索性/观察性判定。它**从来就不是「疑似威胁被
  降级」**，而是这条规则本身设计上就只做信息展示，不代表任何安全担忧。目前只有
  `domain_scatter`（域名分布过散）用这一级——报告里单开一栏，不跟 WATCH 混在一起，避免把
  「跨天验证过、确实降级」的 WATCH 和「压根不是威胁信号」的 INFO 混为一谈。
- **WATCH**：命中过可疑规则，但跨天判定为「稳定复现＝常驻自动化/运维」，或核实到其它证据
  （如 `openai_auth` 轴的跨天真实使用核实）支持良性解释。良性但保留可见性，不进威胁告警清单。
- 只有 **IPv4 目的地**参与横向/纵向端口扫描等绝大多数威胁判定；**域名目的地对这些轴天然免疫**
  → 这就是 REALITY 借用 SNI 不被误杀的结构性原因。例外只有三条：`openai_auth`（§5.4）、
  `domain_storm`（§5.6）与 `mining`（§5.9）——`openai_auth` 和 `mining` 只认精确列举的域名清单，
  `domain_storm` 判的是「持续速率」而非「访问了什么域名」，三者都已用真实数据验证过不会误伤
  REALITY，不改变「域名整体对扫描类判定免疫」这个大原则。

## 5. 单日检测轴（先算每天的 base 严重度）

1. **横向高危端口扫描**：一个 origin 在某高危端口上连了 N 个互不相关公网 IP。
   - 阈值 `(可疑, 恶意)` = 距离目标 IP 数。默认 `(5,20)`；info 的端口 22 特调 `(8,25)`；
     6667/6697/5432 为 `(8,25)`；7001 为 `(20,40)`（理由见下）。
   - 高危端口集：telnet(23/2323)、RDP(3389)、SMB(445)、1433/3306/6379/135/139/21/5900/8291/
     37215/52869/7547/1900（info 另含 22），v1.2.0 另加
     **2375/2376**(Docker 未授权 RCE)、**4444**(Metasploit)、**5601**(Kibana)、**7001**(WebLogic)、
     **9200**(Elasticsearch)、**11211**(memcached)、**2181**(ZooKeeper)、**5984**(CouchDB)、
     **623**(IPMI/BMC)、**6667/6697**(IRC，僵尸网络 C2)、**5432**(PostgreSQL)。
   - **`SHAREABLE_HIGH_RISK_PORTS`（v1.2.0 新增）**：7001/5432/6667/6697/5601/9200/2181/5984
     这些端口确实是攻击面，但**同时存在多客户共用同一台服务器的正当用途**（应用面板、托管数据库、
     IRC 服务器、代理后端），因此**参与**机队共享抑制（§7.2）；telnet/RDP/SMB/Docker 这类正常业务
     根本不会连的端口仍然不参与。
   - > **不要把 27017（MongoDB）加进高危端口集。** 它同时落在 Steam / 起源引擎的游戏服务器端口段
     > 27015-27030 里。实测有 origin 因此被判恶意（「27017 成功连接 53 个互不相关公网 IP」），但它
     > 打的是**整个 27015-27098 段**、目标全在 Valve 网段——是在玩 Steam。**新增高危端口前，先确认
     > 它不落在游戏 / P2P / 代理的常用端口段内**，否则在满是消费级流量的数据集里必然误杀。
2. **纵向单目标端口扫描**：一个 origin 对**同一台** IP 敲了 N 个 ≤1024 端口（nmap 式）。
   - 阈值：warning `(10,20)`、info `(8,15)`。
   - 计数时剔除 `COMMON_SERVICE_PORTS`（80/443/53/22/853/993…），避免把访问某 CDN 的
     80+443+853 误判成扫描。
3. **P2P/BitTorrent**：≥3 个不同 IP 命中 BT 特征端口（6881-6889/6969/1337/51413…）。
   这是**分类标记**（ToS 关注），不是安全严重度。
4. **OpenAI/ChatGPT 鉴权滥用（注册机/token 农场）**：当日鉴权域名（auth.openai.com 等）
   次数 ≥`OPENAI_AUTH_MIN_HITS`(300)，且产品域名（chat.openai.com/api.openai.com 等）次数
   占「鉴权+产品」总量的比例 ≤`OPENAI_USAGE_MAX_RATIO`(5%) → SUSPICIOUS。这是**按比例**判定
   而非绝对次数：正常用户即使经代理/中转访问量很大，鉴权流量也远小于实际产品使用量；只反复
   走鉴权流程、几乎不用产品本身，才是账号农场特征。这是**对域名目的地计数的两条轴之一**
   （另一条是 §5.6 域名并发异常；其余轴仅对裸 IPv4 计数），且只针对这两组精确列举的域名白名单，
   不影响 REALITY/SNI 域名豁免的整体设计。
   不参与 `apply_cross_day` 里 horiz/vert 那套 novelty/streak 升降级（鉴权域名固定就那一两个，
   没有「目标集合」概念可比较新旧）。
   - **跨天真实使用核实（2026-07-31 新增）**：`apply_cross_day` 里单独给这条轴走一个分支——核实
     同一 `(节点, origin IP)` 在**其它任意已加载日期**是否有过 ≥`OPENAI_CROSSDAY_USAGE_MIN`(50)
     次产品域名命中。命中 → 降级 `final_sev=WATCH`，`repeat_note` 写明具体是哪天、多少次，说明
     「当天低产品占比更可能是只刷新了 token、没聊天，而非注册机」；否则维持原判 SUSPICIOUS。
   - **动机**：实测发现过一个真实误判——某 origin 单日 390 次鉴权 / 0 次产品，完全符合触发条件，
     但同一 origin 在另一天有 1777 次真实 chatgpt.com 使用，是个正常重度用户偶尔一天没聊天，
     不是注册机；而已确认的真实注册机连续出现的每一天都是 100% 鉴权、从未有任何一天出现过产品
     域名。这两种模式跨天一比就分得开，逐日独立判定看不出来。
   - 这个核实**只看其它天有没有真实用过产品，不动单日判定本身的两个阈值**（300 / 5% 都没改）。
5. **域名目的地分布过散**：当日不同域名目的地数 ≥`DOMAIN_SCATTER_MIN_DISTINCT`(300)，且没有任何
   单一域名占「全部域名次数」的比例超过 `DOMAIN_SCATTER_MAX_TOP_SHARE`(10%) → 直接判 **INFO**
   （2026-07-31 起从 WATCH 改判 INFO，报告里单独成栏——这条本身是探索性判定，不代表跨天验证过的
   威胁降级，跟真正的 WATCH 混在一起容易误导）。用全量数据校准：
   不同域名数中位数 7，p90≈251，p95≈539，本轴取门槛在 p90 附近。命中通常是两类：共享代理/中转节点
   承载很多不同真实用户的流量（良性），或批量探测/自动化访问大量域名。同样只对域名目的地生效，
   不影响 REALITY/SNI 域名豁免；不参与跨天 streak。
6. **单域名连接风暴（v1.2.0 重写，取代 v1.1.0 的「域名并发异常」）**：判据是**持续速率**
   `rate = count ÷ (末次 − 首次)`，需同时满足当日命中 ≥`DOMAIN_STORM_MIN_HITS`(150)、
   跨度 ≥`DOMAIN_STORM_MIN_SPAN_SEC`(20 秒)、`rate` ≥`DOMAIN_STORM_MIN_RATE`(2.0 次/秒)
   → SUSPICIOUS。三道门槛叠加后，正常浏览、遥测、保活、REALITY 心跳全部出局，只剩真正的
   重试风暴 / 暴力破解 / 刷接口。

   > **⚠️ v1.1.0 的旧规则已被推翻，不要再用 `count ÷ distinct_secs`。** 旧规则拿这个比值当
   > 「并发度」、门槛 2.0，并声称「实测从未超过 1.833」。那次校准只用了两天数据，在后续 25 天
   > 的数据上彻底崩掉：**该轴一条就产出了 2166 条告警，占全部告警的 87%**（其余所有轴加起来
   > 只有 321 条），命中的是 www.google.com、cp.cloudflare.com、apple.com、netflix.com、
   > browser.events.data.microsoft.com 这类域名。
   >
   > 根因：`count ÷ distinct_secs` 量的根本不是「突发」，而是**客户端每次事件同时开几条连接**。
   > 数据里这个比值大量精确等于 7.00（21/3、28/4、35/5、399/57…），正是浏览器每主机 6+1 条
   > 并发连接池的固定倍数——这是网络栈属性，不是行为属性。它对时间跨度完全不敏感：
   > `browser.events.data.microsoft.com` 316 次跨 **22 小时**（平均间隔 4.3 分钟、IPv4/IPv6
   > 双栈各一条 → 比值 2.14）和 `app.wilsonmk.xyz` 399 次挤在 **61 秒**内（0.15 秒一次）
   > 被一视同仁。改用速率后二者相差三个数量级（0.004 vs 6.5 次/秒），干净分开。

   - **明确不做的事**：没有做「多域名扫描/枚举」（同一 origin 短时间内命中大量不同域名）——实测
     发现这个模式和「打开一个广告多的网页、几十个第三方追踪域名瞬间加载」在时间聚集维度上无法
     区分（真实抽样命中的是飞书/微信/紫鸟浏览器等正常办公流量），贸然做会误杀正常重度用户，
     故未采纳。
7. **xref（仅 info）**：同日期 warning 引擎已把该 (节点,origin) 判为威胁 → 在成功日志里佐证。
   **方向是单向的**：info 参考 warning，warning 不参考 info。实测遇到过同一 origin 在 warning 侧
   判 CLEAN、在 info 侧判 MALICIOUS 的情况。
8. **多端口横向扫描（v1.2.0 新增，端口无关）**：横向轴只看高危端口白名单、纵向轴只看 ≤1024 端口，
   两者都覆盖不到「拿一份自定义端口清单横扫整段网段」这种最常见的扫描器行为。本轴不看端口具体是
   什么，只看**形状**：
   - 先求「复用端口」集合 = 在 ≥`MULTIPORT_PORT_MIN_IPS`(3) 个不同 IP 上都出现过的端口
     （剔除 `COMMON_SERVICE_PORTS`、`TORRENT_PORTS` 与机队共享目的地）；
   - 再数有多少台目标 IP 被 ≥`MULTIPORT_MIN_PORTS`(3) 个复用端口打中；
   - 该数 ≥`MULTIPORT_SUSPICIOUS`(warning 8 / info 6) → SUSPICIOUS，
     ≥`MULTIPORT_MALICIOUS`(warning 20 / info 15) → MALICIOUS。参与跨天 novelty/streak。

   **不误伤 P2P**：BT 对端端口是随机的、不在对端之间复用，凑不出「复用端口」集合，天然不触发。

   > **⚠️ 上面四个参数单独用会大量误杀，下面四条降噪是必须的。** 在**以代理业务为主**的数据集里，
   > 「一台 origin 连很多 IP 的很多非常规端口」这个形状本身是二义的——它同时是扫描器的形状，
   > 也是代理/机场客户端的形状。实测被误框进来的良性流量有三类：
   > - **端口映射网关**：每台网关 IP 各自独占一段**连号**端口（8531-8541、8561-8573、8621-8630），
   >   一个端口对应一个后端出口；
   > - **机场订阅节点**：端口不连号，但每个 `(IP,端口)` 连上百次、铺满十几小时，是持续关系；
   > - **Cloudflare 客户端**：目标全在 104.17-19.x，端口是 CF 官方备用端口
   >   2052/2053/2082/2083/2086/2087/2095/2096/8880。
   >
   > **试过而无效的判别量（都实测过，别再走一遍）**：跨目标端口集的核心端口占比、平均 pairwise
   > Jaccard、目标 IP 的 /24 聚集度。真扫描与代理池在这三个量上**完全重叠**——某代理池的 Jaccard
   > 0.329 正好落在真扫描的 0.297~0.392 区间内；某代理网关群全在同一个 /24 里，比扫描器还集中。
   >
   > **真正有效的是端口语义**：扫描器打的是可利用服务（2375/2376/3389/4444/5601/6697），代理池
   > 打的是任意映射端口（8501-8700、20004-20129、30804-30845）。故加四条：
   >
   > | 参数 / 条件 | 作用 |
   > |---|---|
   > | `MULTIPORT_MAX_HITS`(5) | 单个 `(IP,端口)` 命中超过此值 → 持续关系而非探测，不计入 |
   > | `MULTIPORT_MAX_RUN`(5) | 单台 IP 端口集最长连号达此值 → 端口映射网关，整台排除 |
   > | `MULTIPORT_MIN_HIGHRISK`(2) | 复用端口集里至少要有这么多个 `HIGH_RISK_PORTS`（全局语义锚点） |
   > | 逐台锚点 | 每台目标 IP 还必须**自己**被至少 1 个 `HIGH_RISK_PORTS` 打中 |
   >
   > **最后那条逐台锚点不能省。** 只判全局时漏过一个真实误报：某 origin 在**别处**碰过 7001/9200，
   > 就等于给整片 Cloudflare 扇出发了通行证，而那些 CF 目标身上一个高危端口都没有。
   >
   > 四条齐备后，10 个人工判读过的案例 **100% 分开**：4 个真扫描全部保留且仍远超恶意线，
   > 6 个代理池全部排除；告警量 warning 36→8、info 127→6。
9. **挖矿池域名（v1.2.0 新增）**：与 `openai_auth` 同类，对精确特征串清单（`MINING_DOMAIN_HINTS`：
   stratum / nanopool / minexmr / f2pool / ethermine 等）做子串匹配。按**形状分两级**：
   - 命中落在 `MINING_STRATUM_PORTS`（3333/4444/5555/7777/8888/9999/14444/45700/3032/1234）上，
     或单域名命中 ≥`MINING_SESSION_MIN_HITS`(50) → `mining`，**SUSPICIOUS**（这台机器本身在挖矿）；
   - 只在 80/443 上零星访问 → `mining_web`，**INFO**（有人用浏览器看了矿池网站/自己的矿池面板）。

   > 这个分级是实测逼出来的：本轴初版对任何命中都判 SUSPICIOUS 且不设次数门槛，结果 23 条命中
   > **全部**是 443 端口、1-8 次的 www.f2pool.com / static.f2pool.com 等**官网**（某 origin 几乎
   > 每天看一次，像在看自己的矿池面板）。真正挖矿是 stratum 端口上的持久连接、命中数成千上万。

## 6. 跨天关联（核心，`apply_cross_day`）

把 findings 按 `(节点, origin, 轴, 端口/目标)` 签名分组，**沿全局时间线逐天**处理，维护
`prior_pool`（此前所有天的目标并集）与「连续可疑」计数 `streak`：

- `novelty` = 当天目标里不在 `prior_pool` 的比例（新面孔占比）。
- **prior_pool 非空且 novelty ≤ NOVELTY_STABLE(0.5)** → 判 **WATCH**（稳定复现＝自动化），
  `streak` 清零。
- 否则 → 维持 **SUSPICIOUS**，`streak += 1`；一旦 **`streak ≥ ESCALATE_STREAK_DAYS(3)`**
  → 升级 **MALICIOUS**（持续换目标扫描）。
- 单日计数已达恶意线的天：保持 MALICIOUS。
- **缺数据 / CLEAN / WATCH 的那天都会打断 streak**（清零）。
- **回溯降级**：对「未曾升级、跨≥2 天、且某可疑日的目标是其它天目标子集(novelty≤0.5)」的签名，
  把该可疑日降为 WATCH —— 让**首次出现那天不因无历史可比而吃亏**。

**方向性**：降级只往下（SUSPICIOUS→WATCH），升级只靠连续 streak（SUSPICIOUS→MALICIOUS）。
跨天关联**永远不会**把单日计数判定的 MALICIOUS 改掉。

## 7. 防误杀设计（为什么这么判）

1. **扫描类判定不对域名计数** → REALITY/SNI 借用免疫。横向、纵向、P2P 这几条轴只认裸 IPv4，
   域名目的地根本不进入它们的计数——不管 REALITY 借用了多大牌的 SNI、访问量多大，结构上就
   触发不了扫描判定，这是免疫的根本来源，而不是靠白名单挡出来的。
   - 三条例外都不削弱这一点：`openai_auth`（§5.4）与 `mining`（§5.9）只对**精确列举**的域名清单
     生效，借用的 SNI 域名不在名单里；`domain_storm`（§5.6）虽然对任意域名生效，但判的是
     「持续速率」而不是「访问了什么域名」，REALITY 心跳低频、摊到全天远不足 1 次/秒，且总量
     达不到 150 次的门槛。也就是说：**REALITY 借用 SNI 这件事本身，在任何一条轴上都不产生信号。**
2. **机队共享抑制**：同一 `(目的地IP, 端口)` 出现在 `≥FLEET_SHARED_MIN_SERVERS(5)` 个节点
   → 判为批量部署的共享应用（Telegram/Steam/STUN/监控探针/大陆 ISP 探测池等），列入
   FLEET_SUMMARY 末尾并排除出威胁判定。**高危端口原则上不参与此抑制**（攻击目标撞车不算豁免），
   但 `SHAREABLE_HIGH_RISK_PORTS`（§5.1）例外——那些端口有正当的多客户共用用途。

   > **v1.2.0 修正了一处文档与实现不符**：此前这句「排除出威胁判定」对 IP 版**并未实现**——
   > `fleet_shared` 算出来后只传给了报告渲染用于打标签，从来没进过 `analyze_origin`（域名版
   > `fleet_shared_domains` 倒是接上了的）。现已接通。
   >
   > 这处修正是被实测逼出来的：端口 7001 产生了 20 条告警、横跨 20 个互不相关客户，目标全是
   > 同一批云主机 IP 且彼此大量重叠——是某个应用/代理后端。其中一个目的地出现在 6 个不同节点上，
   > 已超过 `FLEET_SHARED_MIN_SERVERS`，却被「高危端口不参与抑制」这条豁免保护住了。接通共享抑制
   > 后 20 条降到 6 条；残余仍是同一现象（端点没跨过 5 节点门槛），故再按端口 22 的既有思路把
   > 7001 的阈值抬到实测良性天花板（15 台）之上，即 `(20,40)`。该端口在这份数据里的精确率是 0/20。
   域名版本同理：同一域名出现在 `≥FLEET_SHARED_DOMAIN_MIN_SERVERS(15)` 个节点 → 判为机队通用
   基础设施（CDN/广告/大厂域名等），从「域名分布过散」轴的统计里剔除（只用于这一个轴降噪，
   不影响其它任何判定）。用 87 台节点全量数据校准：域名覆盖节点数中位数只有 1，p95=4，
   15 已经是远高于噪声线的门槛，抽样看过这个门槛附近全是 CDN/广告 SDK/大厂域名。
3. **纵向轴剔除常见服务端口**，避免 CDN 多端口访问误判。
4. **novelty 稳定性判定**：目标复用＝自动化＝WATCH；只有持续「换新目标」才升级。
5. **首次出现回溯降级**：批处理时用其它天的数据把第一天的稳定签名补判为 WATCH。

## 8. 无状态 & 单日可用性

- 引擎**无状态**：不读数据库、不读上一次的 `result/`，每次都从当前磁盘上的 raw 重算。
- **单日也能跑**：依赖历史的只有跨天判定这一类功能，共两处——① horiz/vert 的跨天降级/升级，
  ② `openai_auth` 的跨天真实使用核实。只有一天时两者都无从取证：稳定自动化无法被证明、其它天
  的真实产品使用也查不到 → 都会保守地停在 SUSPICIOUS（**过报而非漏报**），升级路径（需≥3
  连续天）同样不触发。属优雅降级，其余所有单日轴照常工作。

## 9. 可调参数（都在文件顶部）

| 参数 | 含义 |
|---|---|
| `HIGH_RISK_PORTS` / `TELNET_PORTS` | 高危端口集 |
| `SHAREABLE_HIGH_RISK_PORTS` | 有正当多客户共用用途、因而**参与**机队共享抑制的高危端口 |
| `PORT_THRESHOLDS` / `DEFAULT_THRESHOLDS` | 横向轴 (可疑,恶意) 距离 IP 数阈值 |
| `N_LOW_PORTS_SUSPICIOUS/MALICIOUS` | 纵向轴低位端口数阈值 |
| `COMMON_SERVICE_PORTS` | 纵向轴剔除的常见服务端口 |
| `TORRENT_PORTS` / `TORRENT_MIN_DISTINCT` | P2P 判定 |
| `FLEET_SHARED_MIN_SERVERS` | 共享应用节点数门槛 |
| `NOVELTY_STABLE` | ≤此值算「稳定复现」→ 降级 WATCH（默认 0.5） |
| `ESCALATE_STREAK_DAYS` | 连续可疑几天升级 MALICIOUS（默认 3） |
| `OPENAI_AUTH_DOMAINS` / `OPENAI_USAGE_DOMAINS` | OpenAI 鉴权域名 / 产品域名白名单 |
| `OPENAI_AUTH_MIN_HITS` / `OPENAI_USAGE_MAX_RATIO` | 鉴权滥用判定的次数门槛 / 产品占比上限 |
| `OPENAI_CROSSDAY_USAGE_MIN` | 跨天真实使用核实门槛：其它天产品域名命中 ≥ 此值就降级 WATCH（默认 50） |
| `DOMAIN_STORM_MIN_HITS` / `_MIN_RATE` / `_MIN_SPAN_SEC` | 单域名连接风暴：次数下限 150 / 持续速率下限 2.0 次每秒 / 跨度下限 20 秒 |

| `MULTIPORT_PORT_MIN_IPS` / `_MIN_PORTS` / `_SUSPICIOUS` / `_MALICIOUS` | 多端口横向扫描：端口复用的最少 IP 数 / 单 IP 命中复用端口数 / 可疑与恶意的 IP 台数门槛 |
| `MULTIPORT_MAX_HITS` / `_MAX_RUN` / `_MIN_HIGHRISK` | 多端口轴的三条降噪：持续关系上限 / 连号端口块上限 / 语义锚点最少高危端口数 |

| `MINING_STRATUM_PORTS` / `MINING_SESSION_MIN_HITS` | 区分「真在挖矿」与「只看了矿池网页」的 stratum 端口集 / 持续会话次数门槛 |

## 10. 运行

```
python classify_logs.py        # 先跑，供 info 交叉比对
python classify_info_logs.py
```
两者各自输出每日每节点的报告，以及一份机队级跨天总览。报告与总览按
`MALICIOUS / SUSPICIOUS / WATCH / INFO` 分栏（INFO 单独成栏，不与 WATCH 混排）。每条命中项都带
两行说明：**触发**（命中什么规则、规模、阈值）与**定级**（为何是该级别 / 跨天判定结论）——
判定理由始终可以只凭输出复原。

## 11. 已知边界 / 设计取舍

- origin 是内网 IP；不同节点的相同 origin IP **不代表同一设备**，统计以「节点-IP」为唯一单位。
- 阈值按 24h 快照校准（早期曾按整月合并数据，reason 文案已改为按当日措辞）。
- IP 归属（ipinfo.io）分析是**人工离线**做的，**未写进脚本**（保持脚本纯离线可复跑）。
- 升级需≥3 个**连续自然日**都有数据且都判可疑；**断断续续的可疑（中间有 clean/缺数据）不会升级**，
  这是刻意为之（"连续"语义）。
- 「持续性本身也可能是威胁」这一点：当前仅对「持续+换目标」升级；对「持续+固定目标」判 WATCH。
- 「单域名连接风暴」轴依赖上游的时间戳字段（2026-07-29 起才有）。**旧日期的数据没有这个字段，
  该轴对那些天静默不生效**——不是漏判，是无输入。
- **本引擎是在「以代理/VPN 业务为主」的机队上校准的。** 多条降噪规则（`SHAREABLE_HIGH_RISK_PORTS`、
  多端口轴的四条过滤、7001 的特调阈值）都是针对这个环境里的良性形状——代理池、机场订阅、
  端口映射网关、CDN 备用端口。换到别的环境（比如纯企业内网）这些规则会偏保守，可以放宽；
  反过来，任何新增的高危端口都必须先确认不与该环境的常见业务端口段冲突。
- **`openai_auth` 轴在最近 25 天的数据上 0 命中，代码路径未被实际执行验证过。** 门槛已从 300
  下调到 150（此前 300 高于实测总体上限 251，等于该轴被静默关闭），但「下调后能否正常触发」
  尚未有真实样本验证。
- 尚未逐条人工核验的输出：两个引擎的 SUSPICIOUS 清单、`domain_scatter` 与 `torrent` 的条目。

## 12. 变更记录

### v1.2.0

本版基于 25 天全量数据的**逐份人工判读**（读原始日志、与引擎输出逐条对照）做出，
修掉了三个误报来源与两类结构性漏报。

**漏报修复**

- **新增 `multiport` 轴（多端口横向扫描，端口无关）**。此前横向轴只看高危端口白名单、纵向轴只看
  ≤1024 端口，两者都覆盖不到「拿一份自定义端口清单横扫整段网段」这种最常见的扫描器行为。实测
  有 origin 在按 40~60 分钟周期对整段托管商网段反复扫 2375/2376/5601/6697/7001/8118，旧引擎整台
  节点判「恶意 0 / 可疑 0 / 干净 12」。配套四条降噪见 §5.8。
- **`HIGH_RISK_PORTS` 扩充**：新增 2375/2376(Docker)、4444(Metasploit)、5601(Kibana)、7001(WebLogic)、
  9200(Elasticsearch)、11211(memcached)、2181(ZooKeeper)、5984(CouchDB)、623(IPMI)、6667/6697(IRC)、
  5432(PostgreSQL)。**刻意不含 27017**（与 Steam 游戏端口段冲突，见 §5.1）。
- **新增 `mining` / `mining_web` 轴**：矿池域名此前因「域名对所有轴免疫」而完全不可见。
- **`OPENAI_AUTH_MIN_HITS` 由 300 下调至 150**：实测单日鉴权命中数的总体上限只有 251，
  门槛 300 已高于整个总体，等于该轴被静默关闭（25 天 0 命中）。真正起判别作用的是产品占比（≤5%），
  次数门槛只用来滤小样本。

**误报修复**

- **`domain_concurrency` 轴被推翻，重写为 `domain_storm`**（§5.6）。旧轴一条就产出 2166 条告警、
  占全部告警的 87%，命中的是 Google / Cloudflare / Apple / Netflix / 微软遥测。根因是
  `count ÷ distinct_secs` 量的是「客户端每次事件开几条并发连接」（浏览器每主机 6+1 → 比值恒为 7），
  与时间跨度无关。改用持续速率后，warning/info 侧分别降到 2 条 / 3 条。
- **`multiport` 轴自身的四条降噪**（§5.8）：代理池、机场订阅、端口映射网关、Cloudflare 备用端口
  都会命中这个形状。其中「语义锚点必须逐台判」这一条尤其关键。
- **`mining` 轴分级**（§5.9）：初版把「用浏览器看矿池官网」判成 SUSPICIOUS，23 条命中全部是
  443 端口、个位数次的矿池官网访问。现已拆为 `mining`(SUSPICIOUS) / `mining_web`(INFO)。

**结构性修正**

- **`fleet_shared` 接通 `analyze_origin`**：此前 §7.2 声称的 IP 版机队共享抑制**从未实现**——
  `fleet_shared` 只用于报告打标签，没进过判定逻辑（域名版是接上的）。
- **新增 `SHAREABLE_HIGH_RISK_PORTS`**：区分「正常业务根本不会连」的高危端口（telnet/RDP/SMB/
  Docker，不参与共享抑制）与「有正当多客户共用用途」的高危端口（应用面板/托管数据库/IRC/代理后端，
  参与共享抑制）。
- **`PORT_THRESHOLDS[7001] = (20,40)`**：该端口在本机队有很大的正当共用人群，实测精确率 0/20、
  良性规模上限 15 台，按端口 22 的既有思路抬高到良性天花板之上。
- **xref 补上机队上下文**：`load_warning_status` 此前裸调 `analyze_origin(o)` 不带任何机队参数，
  等于关掉了共享抑制，使 xref 比真正的 warning 跑更敏感；现改为用当天 warning 全量现算一份索引。

**新增可调参数**：`SHAREABLE_HIGH_RISK_PORTS`、`MULTIPORT_*`(7 个)、`DOMAIN_STORM_*`(3 个)、
`MINING_DOMAIN_HINTS`、`MINING_STRATUM_PORTS`、`MINING_SESSION_MIN_HITS`。
**移除**：`DOMAIN_CONCURRENCY_MIN_HITS`、`DOMAIN_CONCURRENCY_RATIO_MIN`。
